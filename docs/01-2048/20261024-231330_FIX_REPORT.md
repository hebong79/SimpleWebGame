## QA-001 — 다중 포인터 감지

- `window` capture 단계에서 페이지 전체의 pointerdown/up/cancel을 관찰합니다. 보드 밖 추가 포인터도 진행 제스처를 즉시 무효화합니다.
- 첫 pointerdown은 capture에서 집합에 등록하고 보드에서 시작하므로 같은 포인터를 두 번째 입력으로 세지 않습니다. pointerup 판정 자체를 capture에서 완료하여 보드 핸들러 이전 정리로 정상 스와이프가 사라지는 문제를 피했습니다.
- 모든 포인터가 끝나기 전에는 거부 상태를 유지하며 기존 reset/destroy의 포인터 집합 정리·캡처 해제·AbortController 해제를 사용합니다.
- 전역 포인터 리스너에는 preventDefault/stopPropagation을 추가하지 않았습니다. 페이지 클릭·스크롤 차단이나 스타일 변경은 없습니다.

## QA-002 — 모달 초점 순환

- 열린 dialog에서 일반 Tab/Shift+Tab만 처리합니다. 매 keydown마다 현재 DOM의 tabbable을 다시 수집하여 첫/마지막 경계에서 반대쪽으로 초점을 순환합니다. 단일 버튼이면 양방향 모두 내부에 유지합니다.
- disabled(비활성 fieldset 포함), 음수 tabindex, hidden/inert 조상, 렌더링되지 않은 요소와 visibility:hidden/collapse 요소를 제외하고 tabindex 순서를 반영합니다. 이전 렌더의 버튼 참조를 보관하지 않습니다.
- 후보가 없으면 Tab의 기본 이탈을 차단하고 dialog에 초점을 유지합니다. 기존 Esc/cancel, 닫은 뒤 초점 복귀 및 blur 보호는 유지합니다.
- Ctrl/Alt/Meta 조합과 Tab 이외의 키는 처리하지 않습니다. 전역 focusin 가로채기나 브라우저 UI의 초점 강제 회수는 없습니다.

## 실제 검증

### 기존 프로젝트 명령

```sh
npm run typecheck && npm test
```

실제 종료 코드 **0**입니다. TypeScript 검사 및 실제 빌드가 통과했고 기존 단위테스트는 **44/44 통과, 실패 0, 건너뜀 0**입니다. 테스트 소스나 expected-failure 설정은 변경하지 않았습니다.

### 증거 파일을 쓰지 않는 추가 브라우저 확인

프로젝트에 설치된 Playwright를 `node --input-type=module -e`로 호출하여 별도 브라우저 context에서 실행했습니다. PM이 이미 실행한 loopback `http://127.0.0.1:3101/`의 갱신된 빌드 파일을 사용했으며 서버를 종료/재기동하지 않았습니다. 두 명령 모두 실제 종료 코드 **0**입니다. 별도 테스트 파일·스크린샷·JSON 파일은 만들지 않았습니다.

1. **Chromium 및 WebKit 자동 확인**
   - 도움말 단일 버튼의 Tab/Shift+Tab 반복 후 dialog 내부 초점 및 document.hasFocus 유지.
   - 재시작 확인의 여러 버튼 사이 양방향 경계 순환, Esc 취소 후 보드 초점 복귀.
   - 실제 브라우저의 PointerEvent 어댑터와 capture shim으로 보드 밖/보드 안 두 번째 포인터 모두 이동 없음.
   - 후속 정상 24px 단일 스와이프는 right 한 번, reset/destroy 이후 이전 제스처 이동 없음.
   - 보드 밖 pointerdown의 defaultPrevented=false.
   - 실제 출력(두 브라우저 동일): `outside:[], inside:[], valid:["right"], reset:["right"], destroy:["right"], blocked:[false]`.
2. **데스크톱 및 모바일 Chromium 자동 확인**
   - CDP Input.dispatchTouchEvent의 실제 브라우저 터치 경로로 첫 손가락 보드 안 + 두 번째 손가락 (20,20) + 첫 손가락 50px 오른쪽 이동/해제를 실행했습니다.
   - 두 context 모두 보드 전체가 이전 값과 동일하고 **0회 이동**이었습니다.
   - 모달을 연 뒤 버튼을 동적으로 disabled/hidden 처리한 경우에도 남은 버튼에서 양방향 순환했습니다.
   - Ctrl+Tab 합성 keydown의 defaultPrevented=false를 확인했습니다. 실제 OS 브라우저 단축키 직접 조작 검증은 아닙니다.

이 검증은 자동화이며 실물 모바일 터치·수동 플레이·실제 음향 청취를 의미하지 않습니다.
