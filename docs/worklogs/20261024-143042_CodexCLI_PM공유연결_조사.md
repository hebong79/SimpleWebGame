- 판정: **공식 지원 경로와 설치 명령 지원을 확인했습니다. 실제 공유 서버·TUI 동시 연결과 메시지 왕복은 아직 실행하지 않았습니다.**

## 권장 구성

사용자에게 보이는 실제 Codex CLI TUI와 대현자의 메시지 전달 클라이언트를 **같은 app-server 주소, 같은 세션 UUID**에 연결하는 방식입니다. 공식 문서는 CLI의 --remote 연결과 app-server WebSocket 리스너를 설명합니다.[1] CLI 공식 문서에는 agents, queue, /rename 명령이 있습니다.[2]

```text
대현자 PM ── queue로 지시 ─┐
                          ├─ 같은 Codex 서버 / 같은 전용 세션
마스터의 실제 Codex CLI ───┘
```

실제 CLI 화면은 별도 콘솔 또는 VS Code 하단 터미널에서 실행하는 후보입니다. 파일 로그 감시창이나 STATUS.md를 네이티브 에이전트 화면으로 표현하지 않습니다. 이름 cody-02는 표시·관리용이며, PM 연결은 정확한 UUID로 대상을 지정하는 편이 안전합니다. 공식 queue는 UUID 또는 정확한 세션 이름을 받습니다.[2]

## 연결 예시 — 실행 전 검증용 설계, 현재 실행한 명령이 아닙니다

다음은 일반 `codex`가 위 신규 번들 바이너리를 가리킨다는 전제의 개념 예시입니다. 현재 PATH의 구버전을 그대로 사용하면 agents/queue가 다릅니다. 43123은 예시 포트이며 사용 가능 여부를 아직 검사하지 않았습니다.

```sh
codex app-server --listen ws://127.0.0.1:43123
codex agents --remote ws://127.0.0.1:43123
codex queue --remote ws://127.0.0.1:43123 --thread <UUID> --message "작업 지시"
```

공식 문서의 `/rename cody-02` 방식으로 대화를 식별하기 쉽게 이름 붙이는 기능도 확인했습니다. 설치 TUI 안에서 실제 이름 변경은 실행하지 않았습니다.[2]

핵심은 별도 exec resume 프로세스들이 같은 저장 세션을 각각 소유하는 구성이 아니라, **공유 서버가 세션을 소유하고 사용자 UI와 PM이 그 서버를 이용**하는 구성입니다. 기존 active writer 문제를 무시하거나 잠금을 지워 해결하는 방식은 사용하지 않습니다.

- 미실행: 서버 시작/포트 바인딩, 실제 TUI 창 표시, 동일 UUID에 PM queue 메시지 전달과 화면 갱신, 표시 이름 지정, 수정 작업.
- 현재 VS Code **Codex 사이드바 채팅 패널 자체**에 외부 PM을 연결하는 기능은 이번 조사로 확인한 것이 아닙니다. 먼저 명령 지원을 확인한 실제 CLI/TUI 경로가 우선 후보입니다.
- 실행 시 모든 구성요소는 같은 신규 바이너리를 사용하고, loopback에만 리슨하며, 전용 세션 UUID와 기본 read-only를 유지해야 합니다. 공개/공유 네트워크로 서버를 노출하지 않습니다.[1]
- 기존 cody-01과 다른 앱 소유 세션은 접근·강제 종료하지 않았습니다. cody-02를 공유 서버에서 재개한다면 기존 exec 실행기와 동시 writer가 생기지 않도록 운영을 전환해야 합니다.
- Hermes PM 런타임을 Codex 런타임으로 바꾸거나 전역 모델/인증 설정을 변경할 필요가 있는 것으로 결론 내리지 않았습니다. 서버/CLI/모델 호출이나 실제 연결은 이번에 수행하지 않았습니다.
- 후속 구현의 수용 기준: 사용자가 실제 CLI 채팅 화면을 보고, 대현자가 보낸 고유 challenge가 그 화면에 나타나며, 같은 UUID의 응답을 PM도 수신하는지 실측합니다. 그 전에는 연결 완료로 표현하지 않습니다.
