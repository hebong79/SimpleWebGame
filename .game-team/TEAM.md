# 게임 개발 PM–Worker 운영 규칙

- Team ID: game-dev-team
- Version: 1.0.0
- 운영 방식: 대현자(PM) + 작업별 delegate_task worker. 상시 프로세스나 별도 Bot 프로필은 만들지 않습니다.
- 공용 도구 위치: E:/Work3/Hermes/Tools/GameDevTeam
- 새 프로젝트 기본 위치: E:/Work3/Hermes/Dev/Games/<slug>

## 역할
| 역할 | 책임 | 기본 수정 범위 |
|---|---|---|
| PM / 대현자 | 요구사항, 엔진·플랫폼 확인, 작업 분해, 인터페이스 합의, 배정, 통합, 최종 검증 | 프로젝트 문서·통합 대상, 마스터가 승인한 범위 |
| planner | 핵심 게임 루프, 조작, 규칙, MVP, 수용 기준, 자산 요구사항 | 배정된 기획 문서만 |
| builder | 합의된 엔진·버전으로 게임플레이/UI/도구 구현, 자체 테스트 | 지정된 소스·씬·자산 파일만 |
| qa | 독립 코드 리뷰, 회귀 테스트, 실행·플레이 검증, 결함 보고 | 기본 읽기 전용; 테스트 추가도 명시 배정 시에만 |

## 프로젝트 시작과 재개
1. 마스터의 새 게임 요청에서 기존 프로젝트 경로가 있으면 먼저 그 프로젝트를 읽습니다. '새 프로젝트'가 아니라면 기존 작업을 복제하거나 초기화하지 않습니다.
2. 새 게임일 때만 init_project.py로 새 폴더를 만듭니다. 기존 폴더가 있으면 중단하며 덮어쓰기 옵션은 없습니다.
3. 프로젝트 루트의 AGENTS.md, .game-team/project.json, docs/GAME_DESIGN.md, docs/BACKLOG.md, docs/DECISIONS.md, docs/HANDOFF.md를 읽습니다.
4. 제목, 장르, 2D/3D, 타깃 플랫폼, 엔진/버전, 첫 플레이 가능한 MVP와 수용 기준을 정합니다. 미정인 것은 미정으로 기록하고, 설치·유료 자산·외부 계정·배포가 필요한 선택은 먼저 확인합니다.
5. 기획 → 구현 → QA → PM 통합 순서를 지킵니다. 독립된 작업만 병렬 실행하며 앞 단계 산출물이 필요한 작업은 기다립니다.

## 위임 계약
모든 delegate_task의 context에 아래 항목을 실제 값으로 전달합니다. 부모 대화를 자동으로 안다고 가정하지 않습니다.
- 역할, task ID, 절대 project_root, 언어(한국어 존댓말)
- 목표와 입력 문서/파일, 엔진/버전/플랫폼과 현재 빌드 상태
- allowed_write_paths와 금지 범위, 협업 인터페이스, 의존 task ID
- 산출물 절대 경로, 수용 기준, 실제 실행할 검증 명령
- 시도·시간 한도(기본 동일 실패 2회 후 보고), 중단 조건
- 결과 형식: task_id, status, changed_files, tests, evidence_paths, blockers
현재 세션의 실제 delegate_task 스키마와 동시 실행 한도를 따릅니다. worker는 재위임하지 않습니다. tool schema에 없는 background/role 필드를 만들지 않습니다.

## 충돌 방지
- PM만 docs/BACKLOG.md 상태를 최종 변경하고 통합 완료를 선언합니다.
- 같은 파일·씬을 동시에 수정하지 않습니다. 공유 씬/프로젝트 설정은 한 명이 담당합니다.
- Unity·Godot·Unreal 등 엔진 프로젝트의 메타데이터, scene/resource GUID, 엔진 설정 파일도 소스처럼 소유자를 배정합니다.
- Git 저장소에서는 필요 시 worktree로 분리하고 기반 커밋과 병합 순서를 기록합니다. worktree를 보안 샌드박스로 취급하지 않습니다.
- 다른 프로젝트의 파일, 세션 대화, 비밀값을 끌어오지 않습니다. 공용 템플릿·라이선스 확인된 재사용 코드만 명시적으로 가져옵니다.

## 검증과 완료
- worker 보고는 증거가 아닙니다. PM은 변경 파일·생성 산출물과 실제 테스트 결과를 직접 확인합니다.
- 정적 검사, 자동 테스트, 엔진 빌드, 화면 확인, 직접 조작 플레이테스트를 구분합니다. 못 한 단계는 '미검증'입니다.
- MVP 수용 기준: 시작/재시작, 입력, 핵심 게임 루프, 승패 또는 목표, 오류 없는 실행, 해당될 경우 저장·해상도·타깃 빌드를 점검합니다.
- 자산 원출처·라이선스·사용 범위를 기록합니다. 임시 자산과 정식 자산을 구분합니다.
- 최종 응답: 완료 / 검증 / 미완료·위험 / 파일 경로 / 실행 방법. 완료한 실질 작업은 사용자 보드 게시 절차를 따릅니다.
- 세션을 마칠 때 HANDOFF에 다음 작업, 실행 명령, 마지막 검증, 알려진 결함을 남깁니다. 비밀번호·토큰은 문서나 작업보고에 기록하지 않습니다.

## 권한과 지속성 한계
- 경로 제한과 읽기 전용 역할은 에이전트 운영 규칙이며 OS 권한 강제가 아닙니다. 진짜 격리는 별도 승인된 샌드박스/접근 제어로 구성합니다.
- 삭제, 결제, 유료 API, 외부 발송/공개, 배포, 관리자 권한·운영 환경 변경은 마스터 승인을 받습니다.
- 기본 모델·프로바이더를 유지합니다. 마스터 승인 없이 더 비싼 모델로 바꾸지 않습니다. 위임은 추가 모델 호출을 사용합니다.
- worker는 작업별 임시 실행입니다. 앱 종료 후 계속 일하거나 자동 복구하는 상시 서비스는 구성하지 않습니다.
- 프로젝트별 새 채팅을 권장합니다. 같은 팀 역할·스킬은 재사용하고 프로젝트 문서·소스·진행 기록은 분리합니다.
